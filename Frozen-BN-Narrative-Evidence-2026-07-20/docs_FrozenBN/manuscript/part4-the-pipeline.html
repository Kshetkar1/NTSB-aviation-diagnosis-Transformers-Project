Part 4 — The Pipeline: How a Narrative Becomes Evidence

This is the accepted architecture, one step at a time. Nearly all of it lives in a single file — Frozen-BN-Narrative-Evidence-2026-07-20/code/query_to_bn.py — with retrieval support from shared/code/main_app.py and the network from code/bn_upgraded.py.

Step 0 — Redact the outcome sentences (before anything else touches the text)

NTSB narratives frequently state the final outcome ("the airplane was destroyed", "the passenger was fatally injured"). Predicting an outcome from text that states the outcome is not prediction (Part 1 called this leakage). So the very first operation on every narrative is redact_severity_phrases() in code/query_to_bn.py — a deterministic list of regular expressions that strips stated injury/damage phrases, death and medical wording, and NTSB's full-report boilerplate. Every downstream consumer — embedding, retrieval, both parsers — receives only the redacted text.

What we did earlier that was wrong. Originally we redacted only before embedding; the deterministic parser still read the raw text. Fixed during the July review pass so all parsing happens on redacted text — the rerun left every headline number unchanged, which itself became evidence that no predictor was feeding on the stated outcomes. Part 7 tells the full leakage story, including exactly what redaction can and cannot remove.

Step 1 — The deterministic parser: hard evidence

parse_query_to_bn_evidence() scans the redacted narrative for NTSB's own vocabulary — occurrence types, flight phases, event keywords — with rule-based matching. When it finds "fire" or "gear collapsed", it produces evidence for the matching network nodes. This is tier 1 of the parser: no model, no randomness, auditable line by line, and sufficient for 176 of the 296 held-out narratives. An optional tier 2 (an LLM reader, Part 3.4, code in code/llm_evidence.py) handles narratives the rules cannot, with its outputs assigned data-measured strengths rather than trusted directly.

Step 2 — Retrieval: soft evidence from similar accidents

The redacted narrative is embedded (get_embedding() in shared/code/main_app.py, disk-cached for determinism) and compared against the ~1,700 pre-computed window narrative embeddings. From the top-100 most similar historical accidents, retrieval_facts() in code/query_to_bn.py reads which coded events those neighbors actually had, and with what frequency. If 71 of 100 neighbors had a landing phase code, "phase = landing" becomes a piece of soft evidence with strength 0.71.

Vocabulary — why the strengths are honest. The confidence attached to each soft fact is an empirical retrieval frequency — the fraction of neighbors exhibiting the code — not a tuned dial. Nothing is fitted; the number is a measurement of the historical record. (Early drafts called this "calibrated", which suggests a fitting procedure that does not exist; the wording was corrected during review — a small example of claim hygiene.)

Step 3 — The k-NN severity readout: virtual evidence on the outcome nodes

The same 100 neighbors have coded injury and damage outcomes. Their outcome distribution (e.g. 62% substantial / 21% minor / …) enters the network as virtual evidence on the injury and damage nodes — Pearl's mechanism from Part 1, implemented via pyAgrum's evidence API. This predictor is called bn-sev and it is the primary severity predictor of the paper.

Vocabulary — what the network does with it (and does not). When virtual evidence on a node faces no competing evidence, the posterior reproduces the input distribution — the network mediates the signal losslessly. A self-test inside the evaluation script asserts this to four decimals before any scoring is allowed to run (selftest_virtual_evidence in tests/frozenbn_heldout_narrative_bn_eval.py). Consequence, stated in the paper without embarrassment: bn-sev's accuracy equals the raw k-NN readout's accuracy (0 of 296 predictions differ). The network adds no accuracy — it adds the reasoning layer: joint posteriors over all nodes, evidence composition, what-if queries, per-node explanations.

Step 4 — Inference and output

With evidence loaded, the network computes posteriors for every node (posteriors() in the evaluation script; the demo app apps/frozenbn_streamlit_diagnosis_prognosis_demo.py shows the same thing interactively). The top-1 predicted state of the injury and damage nodes is what gets scored in Part 5; the full distributions feed the probabilistic metrics (Brier score).

4.1 The negative result we report on purpose: bn-fused

What happens if you fuse everything at once. The "obvious" architecture is to load the event evidence (Steps 1–2) AND the k-NN severity evidence (Step 3) into one inference and let the network combine them. We built that predictor — bn-fused — and it collapses: 38.5% injury / 41.9% damage, worse than the majority-class baseline on injury. The reason is double counting: the event evidence and the severity evidence are both derived from the same narrative, so the network treats one signal as two independent confirmations and over-updates — a textbook violation of the independence assumption behind evidence combination. The fix is the architecture itself: event evidence answers diagnosis questions; the severity readout answers severity questions; they are not fused for the severity task. We publish bn-fused's failure as an ablation because it justifies the design.
Vocabulary — ablation. An experiment that removes or rearranges one component to show what that component contributes. The paper's ablations: retrieval-sev (remove the network → same accuracy, proving where the signal lives), bn-fused (fuse everything → collapse, proving why the paths stay separate), hard/soft/hard+soft (parser-only paths → 82.4%/50.7% at best, proving retrieval carries the severity signal).
