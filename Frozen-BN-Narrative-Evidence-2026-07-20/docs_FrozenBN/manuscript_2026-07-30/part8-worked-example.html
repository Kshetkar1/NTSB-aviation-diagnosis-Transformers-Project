Part 8 — Worked Example: Bird Strike → Forced Landing

This part walks one accident from typed narrative to network posteriors. The scenario is new — we deliberately avoid the examples already used elsewhere (engine fire, windshield failure, landing-gear collapse, LOEP). Here: a single-engine piston aircraft hits birds during initial climb, loses power, and executes a forced landing in a field.

8.1 The synthetic narrative (after redaction)

Imagine a user pastes this text into the demo app. Outcome-stating sentences have already been removed by redact_severity_phrases() — the investigator's final injury/damage verdict is not in the text the system reads.

During the initial climb after takeoff, the pilot reported a loud thump and a sudden
loss of engine power. The pilot observed multiple birds near the departure end of the
runway. Unable to maintain altitude, the pilot turned back toward the airport but could
not reach the runway and landed in a field short of the threshold. The airplane struck
terrain and came to rest upright. Emergency services responded.
Vocabulary — synthetic but pattern-faithful. This narrative is composed for teaching; it mirrors real NTSB wording for bird-strike / power-loss / off-airport landing cases. The pipeline steps are identical to what runs on real held-out accidents in code/query_to_bn.py.

8.3 Step-by-step evidence

Step A — Hard evidence from the parser

The deterministic parser matches NTSB vocabulary in the redacted text:

Text phraseNetwork node (illustrative)Evidence type
"loss of engine power"loss of engine power occurrenceHard (Yes, p=1.0)
"initial climb" / takeoff contextphase: climb or takeoff phaseHard or soft
"birds"environment / wildlife-related nodes if lexicon hitsHard if exact match
"landed in a field"off airport landing / forced landing nodesHard if matched
"pilot"person: flightcrewHard (common — 143/296 held-out)

Hard evidence means: if the narrative names the fact in NTSB's own vocabulary, that node is set to Yes with probability 1. No learned weights.

Step B — Soft evidence from retrieval

The narrative is embedded and compared to ~1,700 window accidents. Suppose the top-100 neighbors include many bird-strike, power-loss, and forced-landing cases. Retrieval counts fractions:

Neighbor fractionExample soft factStrength
38/100 had bird/wildlife codedEnvironment-related finding0.38
71/100 had climb/takeoff phasePhase = climb0.71
52/100 had power loss codedLoss of engine power0.52
44/100 had off-airport landingForced / off-airport landing0.44
Vocabulary — measured fraction, not a tuned weight. Each strength is literally "what fraction of my 100 most similar historical accidents had this code?" Nothing is fitted on the held-out set.

Step C — Prognosis channel (bn-sev)

From the same 100 neighbors, count their coded injury and damage outcomes. Illustrative distribution:

This vector enters the injury node as virtual evidence (Jeffrey conditioning). Top-1 prediction: None (41%). The network posterior reproduces this input when no competing evidence is on the injury node — the self-test in tests/frozenbn_heldout_narrative_bn_eval.py asserts this to four decimals.

8.6 What-if query (what the BN adds beyond retrieval)

Why we did this. Accuracy comes from retrieval; the BN's value is interrogability. Example what-if on this scenario:

Question: "If we assume there was no bird strike (Environment evidence removed), how does P(substantial damage) change?"

The network re-propagates with that node pinned or softened differently. Every node's posterior updates jointly — something a neighbor-count table cannot do in one coherent step. This is the reasoning claim, not the accuracy claim. On held-out fire prediction, this joint structure did not beat retrieval (Part 7.6); we narrow the claim accordingly.
